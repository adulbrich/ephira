# ADR 0002: Data migrations are hand-written, and never guess at lost links

- **Status**: Accepted
- **Date**: 2026-08-18
- **Context commit**: 249566d

## Context

`PROJECTSTRUCTURE.md` said the `/drizzle/` folder is generated by drizzle-kit and must not be edited by hand. That was correct, and untested: all four existing migrations are pure DDL, which drizzle-kit does generate.

The orphaning defect (#181) needs something drizzle-kit cannot produce. `setupEntryTypes` deleted Moods, Symptoms and Medications without first deleting the entry rows referencing them. Foreign keys are off on device, because the app ships no `PRAGMA foreign_keys` anywhere, so those deletes succeeded and left `mood_entries`, `symptom_entries` and `medication_entries` rows pointing at ids that no longer exist. Fixing the delete order stops it happening again; it does nothing for the rows already stranded on an upgrading user's device.

The schema does not change, so there is no diff for drizzle-kit to generate. The work is entirely in the rows.

## Decision

**Data migrations are written by hand in `/drizzle/`, and this is the documented exception to that folder being generated.** A hand-written migration adds four things: the `.sql` file, a `drizzle/meta/_journal.json` entry, a snapshot copied from the previous one with a fresh `id` and the previous `id` as `prevId`, and the import in `drizzle/migrations.js`.

**Orphaned data is deleted, not re-linked.** The migration deletes entry rows whose catalogue item is gone rather than trying to match them back by name.

## Rationale

The alternative to amending the convention is routing around it: a repair that runs from application code at startup, which is a migration that has to work out for itself whether it has run before. The convention was written before this case existed; amending it is cheaper and more honest than pretending it still covers everything.

On not re-linking: the ids are gone, so matching would be a guess. Names are the only thing left to match on, and the catalogue is user-editable, so a wrong guess silently rewrites someone's health history and looks exactly like a right one. The data is already unreachable from the app. Deleting it acknowledges a loss that has already happened; re-linking would manufacture a record that was never true.

The snapshot copy is bookkeeping for drizzle-kit, not for the runtime. `useMigrations` reads only the journal and the SQL. Keeping the snapshot chain unbroken means the next `drizzle-kit generate` still diffs against the right base.

## Consequences

- Hand-written migrations are not covered by drizzle-kit's guarantees, so each one gets a test. `db/__tests__/orphanedEntriesMigration.test.ts` seeds the damaged state with foreign keys off, replays just that migration, and checks `PRAGMA foreign_key_check` comes back empty.
- Every future data migration must be idempotent, because a migration that has already run on some devices and not others is normal.
- Foreign keys stay off on device. Turning them on is a larger change with its own failure modes on existing installs, and is not required to fix this.

## When to revisit

If a data migration ever needs to preserve rather than discard, this decision does not cover it. That case needs its own record, because the argument here rests on the data already being unreachable.
